# 035 — Route channel-delimited reasoning to `reasoning_content`

**Status:** Accepted (gate-approved 2026-06-30) — **IMPLEMENTED v0.10.232** (`deabfe69`); **amended 2026-09-23/24 (#198)** for the close-tag-only reasoning form (Qwen3.5's `<think>…</think>`) — see "Amendment" below, the operator-ruled "Correction (round 3)" that keeps "Universal, not model-gated" true by deriving the decision from the rendered prompt instead of a model-name guess, and the operator-ruled "Correction (round 7)" that closes `.awaitingOpenTag`'s residual `<think>`-in-prose risk by recognizing the marker only when it opens the completion. This line read "implementing" from the moment the code landed; corrected #193 against the tree. Live: `ReasoningChannelFilter` + `splitReasoningChannel` (Gemma), `QwenThinkFilter` + `splitQwenThink` + `qwenReasoningMode` (close-tag-only form, start-anchored `.awaitingOpenTag`) — all in `Sources/AthenaServerKit/ReasoningChannel.swift`; `ReasoningPromptTail` (the prompt-derived signal) in `Sources/AthenaCore/ReasoningPromptTail.swift`.
**Date:** 2026-06-30
**Milestone:** TBD (tool-calling / reasoning correctness)
**Relates to:** ADR 034 (tool_choice:auto un-forcing surfaced this), ADR 013 (`/v1` OpenAI-compat surface).

## Context

`gemma-4-26b-a4b-it` (and its family) emit a **channel-delimited** output format as **literal text** (the markers are NOT registered special tokens):

```
<|channel>thought
…reasoning…
<channel|>…final answer…
```

(tokenizer_config: `soc_token: "<|channel>"`, `eoc_token: "<channel|>"`, plus an `x-regex` splitting output into `thinking` / `tool_calls` / `content`.) The chat template **forces the thought channel on whenever `tools` are present** (`{% if … or tools %}`), so it cannot be suppressed via `enable_thinking`.

The substrate's `.gemma4` tool parser (`ToolCallProcessor`) strips **tool-call** markers (`<|tool_call>…<tool_call|>`) but has **no concept of the thought channel**, so `<|channel>thought…<channel|>` falls straight through into the `content` stream — the observed token leak.

It was invisible until now because ADR 034's old forced path masked all output to pure tool-call JSON (no channel tokens possible). Free generation (what `auto` now uses, and what plain chat already used) surfaces the model's native format. This is therefore a **pre-existing reasoning-format gap**, exposed — not an ADR 034 regression.

## Decision

Parse the channel-delimited reasoning out of the content stream and surface it as OpenAI **`reasoning_content`** (operator-approved over dropping it — preserves chain-of-thought for clients that want it; keeps `content` clean for those that don't).

1. **MLX-free reasoning filter** (`AthenaServerKit`, unit-pinned per ADR 008/009):
   - `splitReasoningChannel(_:)` — one-shot split of a complete generation into `(content, reasoning)` for the non-streaming path.
   - `ReasoningChannelFilter` — a stateful streaming splitter (mirrors `StopStreamFilter`'s partial-marker holdback) that routes incremental text to content vs reasoning across chunk boundaries.
   - Strips `<|channel>thought…<channel|>` blocks; the leading channel-name header (`thought\n`) is dropped from the reasoning text.

2. **DTOs:** `ChatMessage` gains `reasoning_content: String?` (non-streaming), `ChatDelta` gains `reasoning_content: String?` (streaming). Both omitted from JSON when nil — plain responses are byte-unchanged.

3. **Wiring:** non-streaming splits the collected text before building the choice; the streaming pump feeds content `.text` through the filter, emitting `delta.content` and `delta.reasoning_content` separately. The Guide-forced tool path (masked JSON, no channels) and the substrate `.toolCall` path are unaffected; the filter applies only to free-generation content text.

**Universal, not model-gated.** The filter keys on the literal `<|channel>`/`<channel|>` strings, which do not occur in normal content, so it is a no-op for models that don't emit them — no per-model branching. (Upgrade path: read `soc_token`/`eoc_token` from tokenizer_config if a future model uses different channel delimiters.)

## Rejected alternatives

- **Drop the reasoning entirely.** Simpler, but discards chain-of-thought a client may want. Operator chose `reasoning_content`.
- **Suppress via `enable_thinking=false`.** Blocked: the template forces thinking on when `tools` are present.
- **Fix in the substrate `.gemma4` parser.** The "right" layer, but a broad change in the vendored fork; the Athena-side filter is localized, testable, and composes with the existing `StopStreamFilter`.

## Consequences

- `/v1/chat/completions` surfaces `reasoning_content` (OpenAI-aligned) for channel-format models; `content` is clean.
- One more stateful streaming filter to maintain (holdback for partial markers).
- Honesty boundary: reasoning extraction is **format-specific** (the `<|channel>` delimiters). Models with other reasoning conventions are unaffected (no-op) and handled by their own mechanisms (e.g. Qwen `enable_thinking`).
- Decision logic MLX-free + unit-pinned (ADR 008/009).

## Amendment (2026-09-23, #198) — Qwen3.5's `<think>…</think>` needed model-gating

**Observed.** `Qwen3.5-27B-4bit`, `temperature: 0`, no `chat_template_kwargs` (thinking on by default): `content` began `Thinking Process:\n\n1. **Analyze the Request:**…`, `reasoning_content` was `null` — the same leak this ADR fixed for Gemma, on a different model. Root cause: Qwen3.5's own chat template pre-inserts the OPENING `<think>\n` into the **prompt** whenever thinking is active (`{%- if enable_thinking is defined and enable_thinking is false %}<think>\n\n</think>\n\n{%- else %}<think>\n{%- endif %}` at the generation-prompt tail, confirmed against the shipped `tokenizer_config.json`'s `chat_template`). The model's own completion therefore carries **only the close marker** — there is no start delimiter in the output to key a marker-only filter on.

**Why this breaks "Universal, not model-gated."** Gemma's filter is safe as a no-op because `<|channel>`/`<channel|>` never occur in ordinary content, and the state machine only ever enters `.reasoning` after it SEES the start marker — an ordinary response from any model that never emits the marker is untouched. Qwen3.5's close-tag-only form has no equivalent: a filter that defaults to "everything is reasoning until `</think>`" would misclassify the entirety of any Qwen response that has no thinking at all (`enable_thinking: false`, or any other model, since `</think>` is not otherwise Qwen-specific in the way `<|channel>` is Gemma-specific-by-construction). There is no text-only rule that stays universal here.

**Decision.** `QwenThinkFilter` (`Sources/AthenaServerKit/ReasoningChannel.swift`) is model-gated via a three-way `Mode` — `.disabled` / `.awaitingOpenTag` / `.reasoningOpen` — resolved by `qwenReasoningMode(modelName:chatTemplateKwargs:isStructured:)` from the resolved model id (a `qwen3.5` substring match on the canonical store id; MLX-free, no `ModelSupport`/config read, since `AthenaServerKit` has no `AthenaLLM` dependency to classify architecture properly), the request's `enable_thinking` (mirroring the template's own default of `true`), and whether the response is schema-guided or a forced tool call — BEFORE generation starts. `.reasoningOpen` streams reasoning tokens live from byte 0, no buffering. `.awaitingOpenTag` watches defensively for a literal `<think>` (paired form). `.disabled` is a TRUE no-op that never scans for either marker. Chained after the Gemma filter in all three call sites (`/v1/chat/completions` non-stream + stream, `/v1/messages` non-stream + stream) so a model that emits neither format is fully unaffected.

**Rejected: buffer-until-decided (stay universal).** A filter that holds ALL output until it either sees `</think>` or reaches end-of-generation, deciding the split only then, needs no model gate — but it would defer the first `content` byte of every plain (non-thinking) response from every model until generation ends, since nothing can rule out a future `</think>` without knowing the model/request. Destroys live streaming UX universally to handle one model's ambiguous format. Rejected.

**Upgrade path (tokenizer_config).** ADR 035's original upgrade path — read `soc_token`/`eoc_token` from `tokenizer_config` — doesn't apply to Qwen3.5: its `tokenizer_config.json` carries no such field (checked directly against the `mlx-community/Qwen3.5-27B-4bit` snapshot); the `<think>`/`</think>` tags are literals baked into the Jinja chat template, not exposed tokenizer metadata. Hard-coded, same as Gemma's markers.

**Correction (2026-09-24, Codex adversarial review on PR #213) — two defects in the first cut of this amendment, both fixed before merge.**

1. **The "model-gate" didn't gate the marker scan, only the initial state.** The first revision's `QwenThinkFilter` always searched for `<think>`/`</think>` in `.content` state, even for a request the caller had resolved as non-Qwen (`expectThinking: false`) — so a literal `<think>...</think>` appearing in ORDINARY content from ANY model (e.g. explaining the tag itself) was silently stripped into `reasoning_content`, breaking the "safe no-op for other models" guarantee this same amendment's own "Why this breaks Universal" section argued for. Fixed by splitting the boolean into the three-way `Mode` above: `.disabled` never touches the buffer's marker search at all, so non-Qwen3.5 traffic is a byte-identical passthrough, guaranteed by construction, not by the heuristic returning the right answer.
2. **Structured/forced-tool-call responses were misrouted into reasoning entirely.** Athena's Guide masks the vocabulary from token 0 for both a schema-guided `response_format` and a forced tool call (`Sources/AthenaLLM/MLXLLMModule.swift`'s own comment: "Structured ⇒ NO-THINK by construction... the model's `<think>…</think>` is suppressed"), so a Qwen3.5 structured/tool-call response never emits `</think>` at all. The first revision defaulted straight to `.reasoningOpen` whenever `enable_thinking` resolved true, with no check for this case — the ENTIRE structured JSON (or the free-form text a forced tool call parses from) was swallowed into `reasoning_content`, and `content`/the parsed tool call came back empty. Fixed: `isStructured` (schema present OR a forced tool call) forces `.awaitingOpenTag` regardless of `enable_thinking`. Live-verified: a `response_format: json_schema` request against `Qwen3.5-27B-4bit` now returns the JSON in `content` with no `reasoning_content` field, where before this correction it would have returned an empty `content`.

Both were caught by the pre-submit cross-model review gate (this repo's `pr-merge-loop`), before either reached `main` — recorded here per the same standard as the amendment itself, since the corrected design (the `Mode` enum, `isStructured`) is now the shipped decision, not the first cut.

**Correction (2026-09-24, round 3) — operator ruling: model-gating itself is rejected; the signal is prompt-derived instead.**

The automated review's round 2 verdict was COMMENTED, not APPROVED: both round-1/2 defects were verified fixed, but it explicitly deferred the underlying architectural call to the operator — reversing this ADR's own "Universal, not model-gated" consequence, and classifying by a `qwen3.5` model-id substring in a target (`AthenaServerKit`) that deliberately carries no `ModelSupport` dependency, were both judged as decisions the reviewer shouldn't make unilaterally.

**Operator ruling.** Model gating is rejected outright — no model-id substring, no classifier, in either direction. The signal is derived from the **actual rendered prompt** instead: after the chat template renders, check whether the prompt ends inside an open reasoning block (the open marker with no matching close marker after it in the prompt's own text). Only then does the completion start in `.reasoningOpen`; everything else stays exactly as ADR 035 already had it — marker-driven, watching for a literal `<think>` before entering reasoning, a no-op unless that marker actually appears in the output. This is genuinely universal: it doesn't ask "is this Qwen," it asks "did THIS prompt open a block it never closed," which is true or false for any model's template, not just Qwen3.5's.

**Where it's computed.** `ReasoningPromptTail.startsInOpenBlock` (`Sources/AthenaCore/ReasoningPromptTail.swift`) is a pure String scan — no MLX, no model classification, testable in the fast tier. It runs on the last `tailTokenCount` (32) tokens of the prepared prompt, decoded back to text. The decode itself needs the tokenizer, so it happens in `AthenaLLM`'s `MLXLLMModule.beginGeneration`, immediately after `container.prepare(input:)` (the exact point the module already reads `lmInput.text.tokens` for the ADR 030 prompt-ceiling check) — the ONE place in the whole request path that already has both the rendered prompt tokens and the tokenizer in scope. The resulting `Bool` (`startsInReasoning`) crosses into the server layer as a new `GenChunk.startsInReasoning` case, emitted once before the first `.text` chunk on every decode path (free-generation, speculative/logprobs, batched) — the server ignores the value whenever `isStructured`, since `isStructured` already forces `.passthrough` regardless (round-4 correction below; this line originally said `.awaitingOpenTag`, stale as of that same round's own commit — round-5 automated review "Claim check").

**Why this is strictly better than the model-name gate it replaces**, not just a different way to reach the same place:
- It fixes the two-directional heuristic failure the round-2 review's follow-up flagged (a differently-named Qwen3.5 convert, e.g. `qwen35-...` with no dot, silently un-fixing the leak; a `Qwen3.5-Coder` variant whose template doesn't pre-open the block getting wrongly gated in) — there is no name to get wrong anymore.
- It naturally covers any OTHER model whose template does the same thing Qwen3.5's does, with zero code changes — the model-gated version would need a new substring for every such model as it's discovered.
- `AthenaServerKit` stays free of any model-identity concept, matching its own stated design (the `ModelHealth`-adjacent MLX-free testable-seam philosophy, ADR 008/009) more faithfully than the round-2 substring gate did.

**`QwenThinkFilter.Mode` simplifies from three cases to two.** `.disabled` (the round-2 fix for "don't scan for `<think>` outside Qwen3.5") is gone — there is no "outside Qwen3.5" concept to gate on anymore. `.awaitingOpenTag` (renamed from nothing — it already existed, formerly reached only via the model-name gate returning non-`.disabled`) is now simply the default for every request whose prompt didn't start already open; it is the same marker-driven design `ReasoningChannelFilter` already uses for Gemma. **Correction (round 4, automated review "Claim check"): this is not the same residual risk as Gemma's, and an earlier draft of this paragraph wrongly claimed it was.** `<|channel>`/`<channel|>` are deliberately non-natural delimiters that don't occur in ordinary content (see this file's own header comment); `<think>` is plain ASCII a model can plausibly emit in ordinary prose (discussing the tag, echoing an agent scaffold), so `.awaitingOpenTag` scanning for `<think>` anywhere in the output was a real, not hypothetical, gap. **Closed in round 7 below** — see "Correction (round 7)". (A third mode, `.passthrough`, is added in round 4 below, for the unrelated case of structured-payload integrity.)

**Live-verified** (`:7449`, throwaway data dir, both checkpoints resident): the original #198 probe (`Qwen3.5-27B-4bit`, plain chat, thinking on) — `content` clean, `reasoning_content` populated, byte-identical to the round-2 result; a `response_format: json_schema` request — JSON lands in `content`, no `reasoning_content`; a plain Gemma request (`gemma-4-e2b-it-4bit`) — `content: "4"`, unaffected, confirming the Gemma path stays byte-for-byte what ADR 035 always specified.

**Gap found and closed in review (house pre-reviewer, same round).** `MLXLLMModule.runOneBatch` (the ADR 039 S2 batched-decode fast path, `BatchScheduler.enabled`, default off) yields `GenChunk` events directly and had no equivalent `.startsInReasoning` emission — a batched free-generation request to a close-tag-only-template model would have silently reproduced the #198 leak. Fixed in the same commit: each batch row already carries its own `promptTokens: [Int]` (`BatchPending`), so `runOneBatch` computes and yields `.startsInReasoning` per row from that, before its first `.text`, mirroring the non-batched path without a second `container.prepare`. Untestable in the fast tier (same as the rest of `runOneBatch` — it's MLX-gated, outside the ADR 008 seam, and was untested before this change too), so this is verified by code inspection and the existing build, not a new unit test.

**Correction (2026-09-24, round 4, Codex adversarial review) — `.awaitingOpenTag` still scanned structured output, silently corrupting it.**

`isStructured` forced `.awaitingOpenTag`, not `.passthrough` — but `.awaitingOpenTag` is not a passthrough, it actively scans for and strips literal `<think>…</think>` pairs. A schema value or tool argument that legitimately contains that text (e.g. a user asking the model to echo it, or discuss it) was silently corrupted: `{"tag":"<think>x</think>"}` became `{"tag":""}` before the JSON reached the client, remaining valid-looking structured data with no error — exactly the "silent corruption" class this review flags as worst-case, since a downstream tool consumer would execute on altered arguments with no signal anything went wrong.

Fixed by adding a true third mode, `.passthrough`: zero marker scanning, every byte is `content`, nothing is ever routed to `reasoning`. `qwenReasoningMode(isStructured: true)` now returns `.passthrough` instead of `.awaitingOpenTag`, and the streaming pump (`foldGenChunks`) initializes its `QwenThinkFilter` to `.passthrough` up front for a structured/forced-tool-call request rather than waiting on `.startsInReasoning` to (not) upgrade it — the same fix, applied at both entry points. Regression tests pin the literal-tag-survives-intact behavior in both one-shot and streaming form (`testPassthroughLeavesLiteralTagsInContentUntouched`, `testStreamingEqualsOneShotPassthrough`) and the mode-selection contract (`testModeStructuredForcesPassthroughEvenWhenPromptOpened`, `testModeStructuredForcesPassthroughWhenPromptDoesNotOpen`). Mutation-verified: reverting `qwenReasoningMode`'s `isStructured` branch to `.awaitingOpenTag` turns exactly those two mode-selection tests red, nothing else.

Live-verified (`:7449`, throwaway data dir): a `response_format: json_schema` request whose schema value is the literal text `<think>x</think>` now returns `{"tag": "<think>x</think>"}` unchanged in `content`, both non-streaming and streaming (`stream: true`) — reconfirmed the three standard checks (plain Qwen3.5, plain Gemma, and the `logprobs:true` decode path from round 3) are unaffected by this change.

Gemma's `ReasoningChannelFilter` has the analogous theoretical exposure (its own markers, `<|channel>`/`<channel|>`, could in principle appear in a schema value too) but is deliberately left untouched here: it predates this PR, the operator's ruling for this PR was scoped to the Qwen filter, and "keep the Gemma tests byte-identical" is a standing constraint on this branch. Tracked as a known gap for a follow-up, not fixed in this PR.

**Correction (2026-09-24, round 7, operator ruling) — `.awaitingOpenTag` now recognizes `<think>` only at the start of the completion, closing the round-4/5/6 residual risk instead of accepting it.**

Rounds 4–6 left one item open: `.awaitingOpenTag` scanned the ENTIRE completion for a literal `<think>`, so an ordinary response that merely discussed the tag (or echoed an agent scaffold containing it) got everything from that byte onward diverted into `reasoning_content`, with no close-tag fallback if `</think>` never arrived. Round 6's automated review correctly reclassified this from a code-correctness blocker to a product/architecture acceptance call and deferred it to the operator rather than block a fourth time.

**Operator ruling.** Close the gap with a narrower rule rather than accept the risk: `.awaitingOpenTag` recognizes `<think>` ONLY when it opens the completion — optional leading whitespace, then the marker, with nothing else in between. Once any non-whitespace byte that isn't part of a leading `<think>` match has been emitted, the filter is **permanently** passthrough for the rest of that completion; a `<think>` appearing later in the output (mid-prose) is just content, and never re-opens reasoning even after a leading `<think>…</think>` pair has already closed once. An unterminated leading `<think>` (cut off by `max_tokens` before `</think>` arrives) correctly keeps everything in `reasoning_content` — that is the template's own close-tag-only shape working as intended, not a new failure mode.

**Why this is sound, not just narrower.** Qwen3.5's own template only ever puts `<think>\n` at the very start of the assistant turn (verified against the live chat template, round 1 of this PR) — it has no mechanism to emit `<think>` mid-response as a legitimate marker. Recognizing the marker only where the template can actually place it removes the mid-response false-positive surface entirely, rather than trying to distinguish "real" mid-response markers from prose ones (which the model's own output gives no way to do). It does not remove the surface at the leading position itself: a completion whose first non-whitespace bytes are a genuinely-requested literal `<think>` (a user asking the model to quote or echo the tag as its very first output) is still read as opening reasoning — that is the same accepted-risk class Codex's round-7 finding restates and this file's "Rejected" note below addresses.

**Implementation.** `QwenThinkFilter`'s internal state machine gains a `.leading` state (`.awaitingOpenTag`'s start) alongside `.reasoning` and a renamed terminal `.content` state (the old `.passthrough` mode's fast-path, now shared with `.awaitingOpenTag`'s post-divergence/post-close terminal state). In `.leading`, the buffer's first non-whitespace character decides the outcome: if what follows is (or could still extend into) `<think>`, hold back and keep waiting; once it definitively diverges — or matches in full — resolve to `.content` (with the buffered leading whitespace surfaced as content) or `.reasoning` respectively. Streaming and one-shot agree by construction (`splitQwenThink` reuses the same filter), and the holdback rule is exactly "hold back only while the emitted prefix is whitespace plus a partial `<think>`" (operator's own phrasing) — no more, no less, so a legitimate response beginning with an innocuous partial match (e.g. `"<thi"` as ordinary text, never completing the marker) is correctly resolved to content once it diverges or the stream ends.

**Tests.** Replaced the test that pinned the old (defective) scan-anywhere behavior with four cases the ruling specified: a `<think>` appearing mid-response stays in content; a leading `<think>…</think>` pair still splits (unchanged from before — the marker is already at the leading position); leading whitespace before the marker still splits, with the whitespace surfaced as content; an unterminated leading `<think>` puts everything in `reasoning_content`. Plus streaming-equals-one-shot coverage for the two cases that exercise the new holdback logic. Mutation-verified: the mid-response case is the one genuinely behavior-differentiating test — reverting to the old "scan anywhere" logic turns it red (old code would split "The " into content and everything after `<think>` into unterminated reasoning) while every other test stays green, confirming the fix's effect is isolated to exactly the case it was meant to close.

**Live-verified** (`:7449`, fresh throwaway daemon, both checkpoints resident): the standard Qwen3.5 2+2 probe (`content` clean, `reasoning_content` populated, unchanged from every prior round), a prose prompt asking the model to explain what the `<think>` tag is (now correctly returns prose in `content` with no `reasoning_content` — the exact case that was previously at risk), a `response_format: json_schema` request (unaffected — routes through `.passthrough`, untouched by this round), and a plain Gemma request (byte-identical, `ReasoningChannelFilter` untouched).

**Review findings, round 7 — two accepted as documented limitations, one rejected, one filed as a follow-up.**

- **Accepted, documented (house pre-reviewer).** `.leading`'s buffer has no `holdback`-style bound the way `.content`/`.reasoning` do: a run of pure whitespace with no non-whitespace character yet is retained in full across pushes. In practice this is bounded by the request's `max_tokens`/decode-length ceiling like everything else in a generation, not a new order-of-magnitude memory exposure, but it does deviate from this file's established per-state bound and has no dedicated test. Documented here rather than fixed — adding a bound would need a policy for "give up and flush as content after N whitespace scalars," which is a design decision, not a bug fix, and the operator's round-7 ruling didn't ask for one.
- **Accepted, documented (house pre-reviewer).** If a tokenizer/BPE quirk ever caused a model's first generated scalar to be an invisible-but-non-whitespace character (`Character.isWhitespace` correctly excludes ZWSP U+200B, WORD JOINER U+2060, BOM U+FEFF, verified directly against the Swift stdlib) before a genuine `<think>` open tag, `.leading` would see that character as "the first non-whitespace," diverge immediately, and permanently fall to `.content` — reproducing #198's original leak via a different trigger. No evidence found that Qwen3.5's tokenizer actually does this (the ADR's justification is about where the TEMPLATE places the marker in the prompt, not what the model's own first generated token decodes to), and untested either way. A genuine, unverified premise gap — flagged rather than silently accepted.
- **Rejected (Codex adversarial review, HIGH).** "Every ordinary unstructured request... including non-Qwen models... a legitimate response requested in XML form such as `<think>value</think>` is rewritten as reasoning solely because it begins with that literal string," recommending gating opening-tag scanning behind model/template metadata. This is not a defect introduced by round 7 — it is the exact "universal, not model-gated" marker convention ADR 035 established for Gemma's `<|channel>`/`<channel|>` on 2026-06-30 (this file's own header comment: "these delimiters don't occur in normal content, so the filter is a safe no-op" — an assumption, not a guarantee, and one that already applies at ANY position in Gemma's output, a strictly broader exposure than round 7's leading-only restriction for Qwen). The operator has now rejected model-gating as the fix for this class of risk three times in this PR's history (round 2's deferral, round 3's ruling, round 6's deferral resolved by round 7's ruling) — Codex's recommended fix is exactly the mechanism already rejected. The `/v1/messages` sub-claim ("extracted reasoning is discarded") is real but unrelated to this round or this PR: confirmed via `git diff 705577b3..5e3e6bf8 -- Sources/athena/Server/AthenaServer+Anthropic.swift` (zero lines changed) and a grep of that file (`reasoning`/`thinking` appears exactly once, in a comment) that the Anthropic dialect has never surfaced a reasoning/thinking content block for ANY model or marker convention — a pre-existing architectural gap outside #198's scope, not a round-7 regression.
- **Filed as a follow-up, not fixed here (Codex adversarial review, MEDIUM).** `collected.logprobs` is passed through to the response unfiltered while `text` has reasoning stripped out of it (`AthenaServer+ChatOpenAI.swift:397-403`, confirmed by reading the code) — for a `logprobs:true` request whose response has reasoning extracted, `choices[].logprobs.content` covers the full raw completion (including the stripped reasoning tokens) while `content` covers only the post-extraction text, so the two arrays don't align token-for-token. Real, and a case this PR's own reasoning-extraction feature causes (before #198, Qwen's output was never split, so nothing diverged). Not fixed in this round: a correct fix needs token-span tracking through the reasoning split (which token index each content/reasoning boundary falls on), not a marker-level string fix, and is new scope beyond the operator's round-7 mandate ("keep this round tight, no new scope"). Filed as GoodOlClint/Athena#218.
